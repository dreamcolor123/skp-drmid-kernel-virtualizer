## 2. Veneer 审计结论与门禁修正

本轮在同一次开机中观察到入口第二条指令的直接分支目标随每次 SDK Hook 发生
固定步长变化。结合 SDK 历史行为确认：

```text
PACIASP
B <allocated trampoline>
...
```

属于 SKP before-hook 逻辑卸载后保留的禁用 trampoline，而非厂商 Binder 原始
veneer。干净重启后，真实入口恢复为：

```text
d503233f d10303ff a9067bfd a9076ffc
PACIASP / SUB SP / STP x29,x30 / STP
```

因此 Resolver 已增加以下共存门禁：

1. 独立校验 SDK 实际覆盖的第一条 4 字节指令；
2. 接受可独立重放的 BTI、PAC 或合法 frame 指令；
3. 拒绝第一条指令直接为 `B` 的入口；
4. veneer 的 Hook 入口与分支目标均须位于 core text；
5. 仅有“可读内核指针 + 类似函数序言”不足以接受目标；
6. 已存在的 SDK allocated trampoline 因不属于 core text 而 fail-closed，避免同一
   开机重复叠加 Hook。

入口语义诊断增加 Hook-site 分类位，但 Kernel Context ABI 20、Control IPC v5、
runtime control v3 的结构和版本均保持不变。
