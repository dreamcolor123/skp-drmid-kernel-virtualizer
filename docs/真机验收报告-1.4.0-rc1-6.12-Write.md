## 2. 一次性期望值与原始路径反向校验

先以 `CONFIG_ONLY` 创建一次性测试 profile，不安装 Hook：

```text

profile fingerprint: fc81f2ff1d76cdb9
expected file: root / 0600 / 32 bytes
```

期望值由经过 CRC 校验的 seed 在内存中按 `global-widevine-v1` 域派生，再通过标准输入
写入设备 root/0600 临时文件。ID 字节未进入命令参数、日志、报告或主机文件。

Hook 安装前执行反向校验：

```text

AIDL IDrmPlugin: 10 次，EUID 2000，stable=yes，expected_match=no
```

两条原始系统路径均与虚拟期望值不同，证明后续 `expected_match=yes` 来自 Write
替换，而非设备真实 ID 偶然等于测试 profile。

## 5. 结束、恢复与清理

两个探针完成后，root/0600 期望文件先行删除，随后前台 runner 正常结束并移除 Hook。
移除瞬间有一个 Binder 调用仍在执行，因此 97064 字节 Kernel Context 按防 UAF
规则保留至重启，Hook 已逻辑禁用。

本轮配置属于一次性前台 runner，未写入已安装模块的持久配置。普通重启后再次执行

## 6. 结论

`1.4.0-rc1` 已通过当前 Linux 6.12 / Android 16 设备的最终 Write 验收：

- 原始 ID 与虚拟 profile 的反向校验成立；
- NDK MediaDrm 与 AIDL IDrmPlugin 共 200 次均稳定命中同一虚拟 ID；
- candidate、correlation 和 write 计数严格闭合；
- 写入、复制、流边界和 pending 生命周期 fault 全部为 0；
- 普通重启恢复原始 Binder 入口，临时状态完成收口；
- Kernel Context ABI 20、Control IPC v5 和 runtime control v3 保持不变。

当前候选满足 `1.4.0-rc1` 发布冻结条件。真实 Linux 6.1 设备仍按 Resolver-only →
单次 Dry-run → 单次 Write 的顺序独立验收。
